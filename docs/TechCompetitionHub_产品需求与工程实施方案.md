# 1. 产品概述

## 1.1 产品定位

TechCompetitionHub
是一个面向所有大学生和科技竞赛参与者的开源成长平台。它以科技竞赛为入口，整合竞赛信息、社区经验、项目成果、能力画像和学习规划，帮助学生完成从"了解竞赛"到"选择竞赛、准备竞赛、展示成果、提升能力"的完整过程。

平台不是单纯的竞赛新闻聚合站，也不是以奖项数量决定个人价值的排名网站。它要提供可核验的信息、透明的评价标准和可执行的成长建议。

## 1.2 产品目标

1.  建立结构化、可维护、可追溯的大学生科技竞赛目录。
2.  让用户可以比较不同竞赛的技术门槛、实践价值、行业认可、投入成本和适配方向。
3.  通过 GitHub Discussions
    建立低成本的经验交流、答疑、组队与项目展示社区。
4.  维护技能图谱、项目案例和学习路线，生成规则透明的初步成长建议。
5.  以开放数据和贡献流程建立可信度，而不是依赖无法解释的黑箱评分。
6.  保持架构可扩展：后续可接入账户、数据库、动态评分、个人档案和 AI
    辅助分析。

## 1.3 非目标（MVP 不做）

-   不在首版自建完整论坛、私信系统、即时聊天或社交关系链。
-   不在首版存储密码、学生证号、身份证、联系方式等敏感个人信息。
-   不宣称评分是官方排名、权威认证或对保研、就业结果的预测。
-   不根据学校、地区、家庭背景等因素给学生做价值判断。
-   不在没有证据的情况下自动验证竞赛获奖、项目贡献或个人技能。
-   不在首版调用必须付费的大模型 API。
-   不把未经授权的付费课程、论文全文、题库或他人作品复制进仓库。
-   不以"奖项数量"作为唯一的个人成长评价指标。

## 1.4 核心用户

  ---------------------------------------------------------------------------------------------------
  用户类型                主要诉求                               首版支持
  ----------------------- -------------------------------------- ------------------------------------
  竞赛新手                找到适合自己的竞赛，了解入门路径       竞赛筛选、难度与前置技能、路线指南

  有经验的参赛者          复盘、展示项目、帮助后来者             项目案例、经验文章、Discussions

  队长/组织者             找队友、规划备赛、拆解技能需求         组队讨论模板、备赛计划模板

  开源贡献者              修订竞赛资料、提交项目、补充来源       Issue、PR、Schema 校验、贡献指南

  教师/导师               推荐竞赛、查看能力要求、分享指导经验   竞赛详情、技能图谱、经验文章

  平台维护者              审核数据、维护评分规则、控制质量       数据状态、审核清单、自动化 CI
  ---------------------------------------------------------------------------------------------------

## 1.5 核心使用路径

路径 A：选择竞赛 1. 用户进入竞赛目录。 2.
按领域、适合年级、报名周期、团队规模、成本和技术方向筛选。 3.
打开竞赛详情，查看官方来源、赛制、适合人群、技能要求、社区评价和数据更新时间。
4. 对比候选竞赛，进入对应经验讨论。

路径 B：生成学习路线 1. 用户选择目标方向或目标竞赛。 2.
勾选自己已掌握的技能，并选择每周可投入时间。 3.
系统用规则引擎对比目标技能与自评技能。 4.
输出技能缺口、阶段任务、建议项目、验收标准和参考资源。 5.
用户根据真实项目成果更新自己的学习进度；首版不将自评包装为已验证能力。

路径 C：贡献数据 1. 用户通过 Issue 提交新竞赛或纠错。 2.
贡献者按模板补充结构化字段与来源链接。 3. PR 自动执行
Schema、链接格式、重复 ID、必填字段和构建校验。 4.
维护者检查来源、时效性和评分依据。 5.
合并后自动部署；重要变更记录在变更日志中。

# 2. MVP 范围与优先级

## 2.1 P0：首版必须完成

### 网站

-   响应式首页，适配手机和桌面。
-   竞赛目录：关键词搜索、领域筛选、适合年级筛选、难度筛选、排序。
-   竞赛详情页：简介、主办方、竞赛领域、赛制、时间信息、目标人群、技能要求、费用/资源成本、官方来源、最后核验时间、评分构成。
-   竞赛价值榜：可按领域筛选，显示总分、维度分、样本量/置信提示。
-   项目成果目录和详情：项目目标、技术栈、个人/团队角色、证据链接、关联竞赛。
-   经验知识库：备赛指南、获奖复盘、项目实践文章。
-   技能目录：技能定义、等级、前置技能、练习任务和关联竞赛。
-   规则式成长规划器：目标选择、自评技能、输出缺口与阶段任务。
-   关于、贡献指南、数据政策、评分方法、隐私说明页面。
-   404 页面、基础 SEO、站点地图、可访问性基础。

### GitHub 社区

-   启用 Discussions。
-   预置分类：公告、竞赛咨询、备赛经验、技术问答、组队招募、项目展示、产品建议、投票。
-   Issues
    模板：新增竞赛、竞赛信息纠错、项目提交、技能/资源建议、缺陷报告。
-   Pull Request 模板和 CONTRIBUTING 指南。
-   Code of Conduct 社区行为准则。

### 工程与质量

-   JSON/YAML 数据 Schema。
-   数据校验脚本。
-   构建、测试、链接/数据检查 CI。
-   GitHub Pages 自动部署工作流。
-   变更日志和评分规则版本。
-   示例数据必须明确标注为示例，不伪装成官方事实。

## 2.2 P1：首版发布后优先迭代

-   竞赛对比功能。
-   收藏功能（仅浏览器本地存储，明确说明不是跨设备账户）。
-   资源筛选与技能关系可视化。
-   社区讨论链接与站内内容互链。
-   竞赛日历视图（只显示已核验的日期）。
-   按用户填写的目标生成可复制/导出的 Markdown 学习计划。
-   项目与竞赛关联的贡献者统计（仅基于公开仓库证据，不推断个人身份）。

## 2.3 P2：需要后端后再做

-   用户账户、OAuth 登录和跨设备个人档案。
-   用户提交动态评分及反刷机制。
-   数据库、审核后台、管理员权限。
-   用户间组队匹配、通知、私信。
-   用户技能证据档案、进度追踪。
-   AI 生成建议、资料摘要和项目分析（需用户授权、明确数据处理规则）。
-   基于真实样本的推荐排序和个性化算法。

## 2.4 MVP 完成定义

以下条件全部满足，才可标记为 MVP 发布： 1. 生产构建成功，部署到 GitHub
Pages。 2. 手机和桌面端核心页面可用。 3. 竞赛目录至少有 10
条经过来源核验的数据；如果不足，显示真实数量，不以虚构数据填充。 4.
每条公开竞赛至少包含名称、唯一
ID、领域、描述、来源、核验日期和数据状态。 5.
评分页面公开方法、权重、版本和数据限制。 6.
所有排行榜都能追溯到其数据字段与计算逻辑。 7. 成长规划器能在没有外部 API
的情况下运行。 8. PR CI 能拦截结构错误、重复 ID 和构建失败。 9.
CONTRIBUTING、CODE_OF_CONDUCT、数据政策、评分方法和隐私说明已发布。 10.
无密钥、访问令牌或个人敏感信息进入公开仓库。

# 3. 信息架构与页面设计

## 3.1 主导航

建议导航： - 首页 - 找竞赛 - 排行榜 - 项目成果 - 技能图谱 - 成长规划 -
经验社区 - 参与贡献

移动端使用折叠菜单；主要操作保持清晰，不在首屏塞入过多信息。

## 3.2 首页

推荐模块顺序： 1. Hero：一句话定位 +
"探索竞赛""制定成长路线"两个主要入口。 2.
快速搜索：输入竞赛名、技术领域或关键词。 3.
领域入口：人工智能、机器人、电子设计、嵌入式、软件开发、数学建模、机械设计、网络安全、创新创业等。
4. 热门竞赛卡片：必须来自真实数据，展示核验状态和最近核验日期。 5.
竞赛价值榜预览：解释分数，不只显示排名数字。 6.
优质项目与复盘：展示可复现、证据充分的内容。 7.
成长规划入口：让用户选择目标并开始技能自评。 8.
最新贡献与社区讨论：链接到 GitHub Discussions。 9.
贡献召唤：新增竞赛、提交项目、修正错误。 10.
页脚：数据政策、评分方法、开源许可证、GitHub 链接、免责声明。

## 3.3 竞赛目录

筛选维度： - 竞赛领域/标签 - 面向对象/适合年级 - 个人赛/团队赛 -
线上/线下/混合 - 技术难度 - 参与成本 -
报名/举办周期（只对有来源的数据启用） - 是否有官方资源/开源案例 -
数据核验状态

竞赛卡片字段： - 名称 - 主办方/组织方（如有可靠来源） - 领域标签 -
适合对象 - 技术难度等级及说明 - 评分状态（正式评分/样本不足/待核验） -
最近核验时间

必须支持空状态、加载失败状态和无结果状态。筛选状态应可通过 URL
查询参数分享；刷新后可恢复。

## 3.4 竞赛详情

推荐区块： 1. 基本信息与状态标记。 2. 一句话说明：竞赛考查什么。 3.
官方来源与关键事实。 4. 参赛形式、对象、阶段、时间信息。 5.
技能要求和前置知识。 6.
技术深度、实践价值、行业认可、竞争难度、成长收益、成本等评分维度。 7.
适合谁/暂不适合谁。 8. 备赛路线与时间规划。 9. 相关项目、教程和复盘。
10. 社区讨论入口。 11. 数据贡献记录、最近核验时间和纠错入口。

所有时间信息必须带年份或明确周期。无法核实的时间显示"待核验"，不猜测当前报名状态。

## 3.5 排行榜

首版排行榜分为： - 竞赛价值榜 - 项目成果榜 -
技能路线/资源榜（按适用范围和证据完整度排序） -
成长案例展示（编辑精选，不称为客观个人总排名）

每个榜单必须提供： - 排名的适用范围 - 评分方法链接 - 分数维度与权重 -
数据来源与更新时间 - 样本量或证据完整度提示 - 并列规则 -
缺失数据处理规则 - 反馈/纠错入口

禁止在证据不足时输出看似精确的个人能力总分。首版不做"全国大学生个人综合实力榜"。

## 3.6 项目成果页面

项目详情结构： - 项目名称、摘要、状态 - 关联竞赛/目标 -
项目类别和技术栈 - 项目仓库/演示/文档链接 -
团队成员角色（仅由提交者提供且得到同意） -
技术难点、解决方案、测试方法 - 复现步骤和运行环境 -
结果、局限和后续计划 - 许可证与第三方依赖说明 - 证据状态与最后核验时间

"项目展示"不等于平台对原创性、质量或获奖真实性作出保证。审核状态应与官方获奖事实分开。

## 3.7 技能图谱

技能条目字段： - 技能 ID、名称、领域 - 简短定义 -
等级描述（入门/熟练/进阶或明确的 0--4 级） - 前置技能 ID -
可验证的实践任务 - 参考资源 - 关联竞赛和项目 - 维护者、来源和更新时间

技能等级建议采用行为描述，而不是抽象标签： - L0：尚未接触 -
L1：能跟随教程完成任务 - L2：能独立完成常规任务并解释关键原理 -
L3：能调试复杂问题、进行设计取舍并完成测试 -
L4：能设计系统、评估方案边界并指导他人

这只是规划用的能力框架，不是认证。用户自评、导师评价、项目证据必须分开记录。

## 3.8 成长规划器

输入： - 目标竞赛/项目/技术方向 - 当前技能自评 -
每周可投入时间（可选） - 计划周期（可选） - 偏好学习方式（可选）

输出： - 目标技能列表 - 技能缺口与前置依赖 - 阶段任务 -
每项任务的验收标准 - 推荐项目或资源 - 每周计划建议 - 风险与假设说明 -
可复制 Markdown 计划

推荐算法首版采用确定性规则： 1. 读取目标所需技能。 2. 读取技能依赖关系。
3. 对用户自评与目标等级做差值。 4.
按前置关系进行拓扑排序；检测循环依赖。 5. 将技能拆成有可验证结果的任务。
6. 根据可用时间调整每周任务量；用户未提供时间时不假设其日程。 7.
输出依据和限制。

不把自评直接转换成"已验证能力"；不承诺获奖、保研或就业结果。

## 3.9 视觉与交互原则

-   采用清晰、现代、技术社区风格，优先信息层级与可读性。
-   先设计桌面和移动端响应式布局，不把桌面版简单缩小。
-   使用统一颜色语义：成功、警告、待核验、错误；不能只靠颜色表达状态。
-   图表必须有标题、单位、数据范围和文本替代说明。
-   支持键盘导航、可见焦点、足够的文字对比度。
-   不使用虚假的用户数、评分数、热门度和"实时"标签。
-   不以动画和视觉效果牺牲加载速度与可访问性。
-   每个页面都有清晰的主操作和空状态。

# 4. 技术架构

## 4.1 推荐技术栈

  ------------------------------------------------------------------------------------------
  层                      选择                                  原因
  ----------------------- ------------------------------------- ----------------------------
  前端                    React + TypeScript + Vite             组件化、类型检查、生态成熟

  路由                    React Router（静态路由需验证 Pages    避免刷新深层 URL 404
                          回退行为）或基于文件/数据的路径生成   

  样式                    Tailwind CSS + shadcn/ui（可选）      便于统一设计系统

  图表                    ECharts 或 Recharts（二选一）         只在确实需要图表时引入

  内容                    Markdown + JSON                       可审阅、可版本控制、适合 PR

  Schema                  JSON Schema + Ajv，或                 在 CI 和构建阶段校验数据
                          Zod（校验器统一选择）                 

  测试                    Vitest + Testing Library；必要时      逻辑、组件与关键路径测试
                          Playwright                            

  CI/CD                   GitHub Actions                        PR 校验与静态部署

  托管                    GitHub Pages                          公共仓库低成本静态托管

  社区                    GitHub Discussions                    避免首版自建论坛

  数据源                  仓库内结构化数据                      可离线构建、可追溯

  未来后端                REST API + PostgreSQL（候选）         账户和动态数据阶段再引入
  ------------------------------------------------------------------------------------------

不要在没有明确需求时同时引入
Redux、复杂状态管理、微前端、服务网格或多种数据校验库。首版优先保持依赖少、构建可重复、贡献门槛低。

## 4.2 架构原则

1.  **内容与展示分离**：页面不硬编码竞赛事实；事实来自数据文件。
2.  **核心逻辑纯函数化**：评分、排序、技能差距和计划生成逻辑不依赖 UI。
3.  **数据校验前置**：错误数据在 CI 中失败，不带病发布。
4.  **静态优先**：首版所有页面可在构建时生成，运行时无需服务器。
5.  **后端可替换**：定义 repository/data access 接口，页面不直接耦合
    JSON 文件读取细节。
6.  **不把浏览器本地存储当数据库**：收藏仅作为本地体验，清除缓存可能丢失。
7.  **安全默认**：不把 PAT、OAuth secret、API key
    放入前端环境变量或仓库。
8.  **可追溯**：公开数据都有来源、核验时间、状态和修改历史。
9.  **可渐进迁移**：未来 API 尽量沿用同一数据模型和业务接口。
10. **避免过度工程化**：首版不部署服务器、不维护数据库、不引入不必要的微服务。

## 4.3 GitHub Pages 约束与部署

GitHub Pages 是静态托管服务，适合 HTML、CSS、JavaScript
和构建后的静态资产；它不运行 Python/Node 服务端 API。公共仓库在 GitHub
Free 计划下可使用 Pages。项目站点默认 URL 形如
`https://<owner>.github.io/<repository>/`，因此必须正确处理 Vite 的
`base` 路径。参考： - GitHub Pages
概述：https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages -
自定义 Actions
工作流部署：https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages -
发布源配置：https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site

建议使用 GitHub Actions 构建并发布： -
PR：安装依赖、格式检查、类型检查、单元测试、数据 Schema
校验、生产构建；不部署生产站点。 - 主分支
push：执行同一套检查，通过后部署 Pages。 - 手动
workflow_dispatch：允许维护者手动触发构建。 - 使用锁文件与
`npm ci`，避免不可重复安装。 - Action
版本固定到经过审查的版本；安全敏感场景优先固定到完整 commit SHA。 -
最小化 `permissions`；部署工作流使用 Pages 所需权限。 - 不在 PR
流程中暴露部署密钥。

GitHub 官方 Pages Actions 文档给出了
`configure-pages`、`upload-pages-artifact` 和 `deploy-pages`
的工作流方式。具体 Action
版本应在实施时查阅官方文档并采用当时受支持的版本，不要机械复制过时配置。

## 4.4 GitHub Discussions 规划

建议分类： - 📢 Announcements（公告，仅维护者发布） - 🧭 Competition
Help（竞赛选择与咨询，Q&A） - 🧪 Preparation &
Retrospectives（备赛经验与复盘） - 💻 Technical Q&A（技术问答，Q&A） -
🤝 Team Up（组队招募） - 🚀 Project Showcase（项目展示） - 💡 Ideas &
Feedback（产品建议） - 🗳 Polls（投票）

为组队帖提供固定模板：竞赛、角色、技能、期望队友、时间安排、联系方式选择（建议使用
GitHub
公开账号或平台内链接，不鼓励公开手机号）。社区置顶说明不得发布敏感个人信息、买卖奖项、代做、抄袭或未经授权的材料。

GitHub Discussions 支持公告、开放讨论、Q&A
和投票等类别；类别管理与权限由仓库维护者控制。参考： -
https://docs.github.com/en/discussions -
https://docs.github.com/en/discussions/managing-discussions-for-your-community/managing-categories-for-discussions

## 4.5 未来后端迁移路径

当出现以下需求之一时再启动后端： - 用户需要跨设备保存个人档案。 -
用户可提交动态评分，且需要去重、限频和反刷。 -
数据量或编辑流程已无法通过 PR 管理。 -
需要细粒度权限、审核后台或通知。 - 需要保存私密数据或受控访问数据。

迁移建议： 1. 冻结并版本化公共数据 Schema。 2. 定义
`CompetitionRepository`、`ProjectRepository`、`SkillRepository` 等接口。
3. 将静态 JSON adapter 实现为首版数据源。 4. 后端阶段实现 API
adapter，保持业务服务层不变。 5. 将公共事实数据迁移到
PostgreSQL，但保留来源和历史记录。 6.
动态用户评分与编辑审核记录单独存储。 7. 使用 GitHub OAuth
等身份提供商时，后端负责校验回调和会话；浏览器不能持有服务端密钥。 8.
在迁移期间保留静态公开页面作为 SEO 和可用性保障。

# 5. 数据模型与数据治理

## 5.1 通用规则

-   每条记录有稳定、不可随意改变的 `id`。
-   字段命名统一使用英文 `snake_case`。
-   时间统一使用 ISO 8601 日期/时间；只有日期时使用 `YYYY-MM-DD`。
-   标签使用受控词表，避免 `AI`、`人工智能`、`Artificial Intelligence`
    被当成三个无关领域。
-   所有来源记录包含标题、URL、来源类型、访问/核验日期。
-   `unknown`、`not_applicable` 和 `pending_verification` 不可混为一谈。
-   数据状态至少区分
    `draft`、`needs_review`、`verified`、`stale`、`rejected`。
-   未核实的信息不显示成确定事实。
-   评分模型有版本号；权重调整要记录原因与生效日期。
-   记录修改历史依赖 Git 版本历史；重要事实变化在 `CHANGELOG.md`
    中说明。

## 5.2 Competition（竞赛）

推荐字段： - `id`：稳定 slug，例如
`national-undergraduate-electronic-design-contest`。 -
`name`：官方名称。 - `aliases`：常见简称。 -
`organizers`：主办/承办组织，区分层级和角色。 -
`domains`：受控领域标签。 - `summary`：简短介绍。 -
`description`：详细说明。 - `audience`：适合对象、年级或资格限制。 -
`format`：个人/团队、线上/线下等。 -
`difficulty`：平台自定义的难度等级和解释。 -
`estimated_cost`：费用范围、币种、依据、是否估算。 -
`skills_required`：技能 ID 与建议等级。 -
`schedule`：报名/比赛/提交时间（仅有可靠来源时填写）。 -
`official_urls`：官网、章程、通知链接。 -
`sources`：所有支撑关键事实的来源。 -
`verification_status`：数据状态。 - `last_verified_at`：最后核验日期。 -
`created_at`、`updated_at`。 -
`scoring_model_version`：采用的评分模型版本（若适用）。 -
`scores`：平台评价维度与依据，不把它伪装成官方分数。 -
`notes`：已知局限和争议。

## 5.3 Source（来源）

字段： - `title` - `url` - `publisher` -
`source_type`：`official`、`organizer`、`institutional`、`news`、`community`、`research`
等。 - `published_at`（可选） - `accessed_at` -
`supports`：该来源支持哪些事实字段。 -
`confidence`：可选的内部证据等级。 - `notes`

证据优先级建议： 1. 官方竞赛网站、官方章程、主办方通知。 2.
主办单位或承办单位的正式页面。 3. 高校官方通知或权威机构资料。 4.
可信媒体报道。 5.
参赛者经验、社区讨论和个人博客（用于经验，不用于替代官方规则）。

高等级来源不意味着来源中的所有陈述都绝对正确；关键事实仍需交叉核对。社区经验不能作为官方报名时间或获奖规则的唯一来源。

## 5.4 Project（项目成果）

字段： - `id`、`title`、`summary` - `domains`、`technologies` -
`competition_ids` - `repository_url`、`demo_url`、`documentation_url` -
`team_contributions`：角色和贡献说明（提交者提供，需获得涉及成员同意） -
`problem_statement` - `approach` -
`reproducibility`：环境、依赖、运行步骤、测试方法 -
`results`、`limitations` - `license` - `evidence_urls` -
`verification_status` - `submitted_by`（首版仅保存公开 GitHub handle
或贡献记录，不要求真实姓名） - `created_at`、`updated_at`

## 5.5 Skill（技能）

字段： - `id`、`name`、`domain` - `definition` -
`levels`：每个等级有可观察的行为描述。 - `prerequisite_skill_ids` -
`practice_tasks` - `resource_ids` - `related_competition_ids` -
`related_project_ids` - `sources` - `maintainer` - `updated_at`

构建时必须检查技能依赖图是否存在循环；若有循环依赖，CI 失败并指出路径。

## 5.6 Resource（学习资源）

字段： - `id`、`title`、`resource_type` - `url`、`language` -
`level`、`domains` - `related_skill_ids` -
`publisher`、`license_or_access_terms` -
`free_status`：`free`、`freemium`、`paid`、`unknown` -
`last_checked_at` - `notes`

不要将"免费可阅读"误写成"允许转载"。只保存标题、简介和原始链接；需要遵守原站版权与访问条款。

## 5.7 Roadmap（成长路线）

字段： - `id`、`title`、`goal_type` - `target_competition_ids` -
`target_project_ids` - `target_skill_levels` - `phases` - `tasks` -
`estimated_hours`（有依据或明确标为估算） - `acceptance_criteria` -
`resources` - `assumptions` - `version` - `updated_at`

## 5.8 Rating（评分记录）

静态首版建议将编辑评分和社区评分分开： - `entity_type` - `entity_id` -
`model_version` - `dimension_scores` - `weighted_score` -
`evidence_summary` - `source_ids` - `sample_size` - `confidence_level` -
`review_status` - `reviewed_at` - `reviewer_role`（不必公开私人身份） -
`notes`

首版不接受任意用户在前端直接改写 JSON。社区意见通过 Discussions/Issue
收集，维护者核验后通过 PR
修改数据。未来开放动态评分时再设计账户、限频、重复投票、异常行为和申诉机制。

# 6. 评分、排序与可信度机制

## 6.1 竞赛价值评分

首版建议使用 6 个维度，所有维度归一化到 0--100： - 技术深度：25% -
行业/学术认可度：20% - 实践与创新价值：20% - 竞争难度：15% -
学习成长收益：15% - 参与成本可承受性：5%

公式：

`total_score = Σ(dimension_score × dimension_weight)`

所有权重相加必须等于
1。权重属于平台方法论，不是客观真理；必须允许通过公开讨论与版本更新调整。

### 维度定义

-   技术深度：技术复杂度、工程整合、理论要求和问题开放度。
-   认可度：主办方与赛事机制的可验证信息、跨机构/行业影响；不能仅凭宣传文案。
-   实践与创新价值：能否产出可验证作品、工程能力、可复用成果。
-   竞争难度：参赛资格、赛制、公开参赛规模与获奖比例（数据可用时）；没有可靠数据则降低置信度。
-   学习收益：技能覆盖、项目积累、复用价值和复盘资源。
-   成本可承受性：费用、时间、设备和团队组织成本。成本越低，该维度分数越高；无数据时不能默认高分。

不要把主办方层级、竞赛难度、获奖比例和行业认可混为同一概念。

## 6.2 缺失数据处理

-   不得将未知维度自动记为 0 或 100。
-   不得悄悄把缺失维度从分母移除后仍使用原始权重。
-   如果采用按已知维度重归一化，必须显示"暂定分数"，公开覆盖率，并限制排名资格。
-   推荐的首版规则：正式排行榜要求关键维度有足够证据；否则进入"资料不足/待核验"列表，不参与正式排名。
-   所有评分必须能追溯到维度依据、来源和模型版本。

## 6.3 置信度与审核状态

建议区分： - `draft`：草稿，不公开或明确显示草稿。 -
`needs_review`：资料待审核。 - `verified`：关键事实已由维护者核验。 -
`stale`：关键资料可能过期。 - `rejected`：资料被拒绝，不进入公开榜单。

证据完整度可以展示为： - 高：关键事实有官方来源，评分理由和来源齐全。 -
中：关键事实有来源，但部分评分依据来自社区经验或估算。 -
低：缺少关键来源，不能参与正式排名。

不要把证据等级与竞赛分数合成一个难以理解的"权威指数"。

## 6.4 排名规则

-   默认仅对 `verified` 且满足最低证据条件的条目排名。
-   总分相同则显示并列；不以名称或更新时间伪装成质量差异。
-   展示总分时同时展示维度分数、评分版本和核验时间。
-   可按领域和目标用户筛选，避免跨领域简单比较。
-   个人成长案例采用编辑精选或证据维度展示，不做缺乏公平基础的全国个人总榜。
-   不使用"官方排名""全国第一"等可能误导的标签，除非引用的是明确的官方排名并标注来源。

## 6.5 防止评分被操纵

首版不开放无身份约束的即时打分。使用： - PR 审核与公开修改历史。 - Issue
记录纠错依据。 - 维护者审核权限。 - 评分方法版本化。 -
对争议分数添加说明，而不是删除合理的不同意见。

未来动态评分需考虑： - 每个账户/实体的评分频率限制。 -
同一用户重复评分策略。 - 异常流量与刷票检测。 -
评分权重与可信度是否独立。 - 申诉与纠错流程。 - 隐私和数据保留政策。

# 7. 技能推荐与学习规划规则

## 7.1 技能差距

每项技能有当前自评等级 `current_level` 与目标等级 `target_level`：
`gap = max(0, target_level - current_level)`

但页面必须注明当前等级来自用户自评，除非关联了明确的项目证据或导师评价。

## 7.2 推荐流程

1.  读取目标竞赛/项目所需技能。
2.  展开技能的前置依赖。
3.  校验依赖图无环。
4.  比较当前自评与目标等级。
5.  按依赖顺序生成学习阶段。
6.  每个技能至少关联一个可执行任务和验收标准。
7.  优先推荐可免费访问、来源明确、内容仍可访问的资源。
8.  若没有可靠资源，明确显示"待补充"，不得编造资源链接。
9.  用户给出时间预算后再分配任务；否则提供阶段顺序而非假装精确的日程。
10. 允许用户复制计划，且在导出中包含前提假设和免责声明。

## 7.3 任务质量标准

不合格任务："学习 Python""掌握机器学习"。

合格任务： - "完成一个读取 CSV、清理缺失值并输出统计报告的脚本；附
README、示例输入输出和至少 3 个测试。" - "在 MCU
上读取传感器并以固定频率输出数据；记录采样周期、误差和异常处理方式。" -
"完成一个可复现的分类实验；固定数据划分，报告指标、基线、依赖版本和失败案例。"

每项任务应包含： - 目标 - 前置条件 - 操作步骤/资源 - 产出物 - 验收标准 -
预计耗时（如有依据，否则标为估算） - 常见失败与排查方向

# 9. 自动化、测试与质量门禁

## 9.1 PR CI 建议步骤

1.  Checkout。
2.  安装 Node LTS 与依赖（使用锁文件、`npm ci`）。
3.  格式检查。
4.  ESLint。
5.  TypeScript 类型检查。
6.  单元测试。
7.  数据 Schema 校验。
8.  ID 唯一性检查。
9.  技能依赖图无环检查。
10. 评分权重合法性检查。
11. 资源与官方链接格式检查；外部网络链接检查可设置为非阻塞或定期任务，避免外站短暂故障阻断所有贡献。
12. 生产构建。
13. 可选的关键页面端到端测试。

## 9.2 测试重点

### 评分引擎

-   权重之和必须等于 1（允许明确的浮点误差）。
-   所有维度分数在 0--100。
-   未核验条目不能进入正式排行榜。
-   缺失数据按既定规则处理。
-   并列规则稳定且可复现。
-   评分模型版本变化能反映在输出中。

### 技能规划

-   不存在前置技能时能正常规划。
-   存在依赖时按正确顺序输出。
-   检测循环依赖并返回可读错误。
-   当前等级高于目标等级时不生成重复学习任务。
-   无资源时不生成虚构 URL。
-   未提供时间预算时不生成精确日程承诺。

### 数据校验

-   重复 ID 失败。
-   错误 URL 格式失败。
-   `verified` 条目缺少关键来源时失败。
-   过期日期或缺失核验日期触发警告/失败规则。
-   未知标签不符合受控词表时失败。
-   竞赛引用不存在的技能 ID 时失败。

### UI

-   手机导航可用。
-   搜索、筛选和排序组合正确。
-   刷新深层链接不出现 404。
-   空状态、无结果状态和加载错误可理解。
-   键盘可操作。
-   关键内容不依赖颜色单独传达。
-   外部链接有明确语义，必要时标明会跳转至 GitHub/官网。

## 9.3 性能与可访问性目标

MVP 验收建议： - 首屏内容不依赖第三方 API。 -
常规目录页在数据量为数百条时仍能流畅筛选。 -
图片使用合适尺寸与懒加载；首版避免大量大图。 -
核心页面通过自动化可访问性检查；人工检查键盘导航与对比度。 -
生产构建不包含开发密钥或调试数据。 - 页面在常见手机视口无横向溢出。 -
站点错误日志和外链失效处理有明确责任人。

# 10. 社区运营与开源治理

## 10.1 贡献流程

新条目： 1. Issue 使用模板提交。 2. 贡献者补充来源、字段和核验日期。 3.
CI 校验格式和关系。 4. 维护者核查事实、版权和评分理由。 5. 合并 PR。 6.
更新变更日志并自动部署。

纠错： 1. 提供错误字段、当前值、建议值、来源。 2.
若争议属于主观评价，进入公开讨论并记录观点。 3.
事实性错误优先修正；评分方法争议通过版本化流程处理。

## 10.2 维护角色

-   Maintainer：产品方向、合并权限、发布责任。
-   Data Reviewer：审核竞赛事实、来源和时效性。
-   Community Moderator：处理不当内容和社区冲突。
-   Contributor：提交数据、项目、资源和代码。
-   Domain Reviewer（可选）：在某个技术领域提供专业复核。

首版一个人可以兼任多个角色，但数据审核与最终发布流程要写清楚。

## 10.3 社区规范

明确禁止： - 伪造获奖、伪造参赛经历或项目成果。 -
代写/代做竞赛作品、买卖奖项或鼓励学术不端。 -
未经授权上传他人源码、论文、课程材料。 -
发布个人敏感信息、骚扰或人身攻击。 - 以广告、刷榜或利益冲突操纵排名。 -
将未经证实的指控作为事实传播。

允许并鼓励： - 有证据的批评与不同意见。 - 标注局限的经验分享。 -
对评分方法提出可验证的改进建议。 - 公开记录纠错、撤回和评分模型变更。

## 10.4 许可证

-   代码：可考虑 MIT 或 Apache-2.0。
-   文档和原创文章：可考虑 CC BY 4.0，但要明确署名和再利用规则。
-   用户提交的第三方作品：遵循其原有许可证，不默认获得转载授权。
-   数据集合许可证需单独评估，尤其是含第三方描述、Logo、截图或受限制信息时。
-   LICENSE 文件应由维护者最终选择；不要把所有内容默认套用同一个许可证。

# 12. 开发里程碑与验收标准

按单人业余开发、每周持续投入估算，计划约 6--8
周；实际时间取决于页面精细度和数据审核量。

## M0：需求与设计基线（第 1 周）

交付： - PRD、架构说明、数据模型、评分方法。 -
导航图和关键页面线框图。 - ADR：技术栈、数据源、部署方案。 -
初始标签词表与 10 条候选竞赛数据计划。

验收： - 产品边界明确。 - 每个核心功能有输入、输出和验收条件。 -
不存在依赖付费 API 才能完成的 P0 功能。

## M1：项目骨架与 CI（第 1--2 周）

交付： - Vite + React + TypeScript 工程。 - 代码规范、测试框架、数据
Schema。 - CI 工作流、Pages 部署工作流。 -
README、CONTRIBUTING、SECURITY、PR 模板。

验收： - 新克隆项目可按文档启动。 - `npm ci`、检查、测试和构建成功。 -
PR 不会直接部署生产站点。 - Pages 的项目路径 `base` 正确。

## M2：核心数据与竞赛目录（第 2--3 周）

交付： - 竞赛数据模型、来源模型、示例 fixture。 -
搜索、筛选、排序、详情页。 - 数据校验脚本与错误报告。

验收： - 所有公开数据通过 Schema。 - 重复 ID、无效
URL、缺失关键来源可被检测。 - 刷新详情深层链接不报 404。 -
筛选条件可以分享和恢复。

## M3：评分与排行榜（第 3--4 周）

交付： - 评分模型及版本。 - 竞赛价值榜。 -
维度分数、证据状态、核验日期、解释页面。 - 评分引擎单元测试。

验收： - 排名结果可重复计算。 - 缺失数据和样本不足不会伪装成确定排名。 -
页面可以追溯每个分数的来源和模型版本。 - 个人能力总榜不在 MVP 范围内。

## M4：项目、经验与技能图谱（第 4--5 周）

交付： - 项目成果目录与详情。 - Markdown 经验文章。 -
技能目录、技能等级与依赖校验。 - GitHub Discussions 链接和投稿入口。

验收： - 项目详情有复现信息、许可证/授权说明和证据链接字段。 -
技能依赖图无环。 - 所有资源条目具有来源和访问状态字段。 -
社区链接不会指向不存在的分类。

## M5：成长规划器（第 5--6 周）

交付： - 目标选择与技能自评界面。 - 技能差距计算。 -
依赖排序和阶段任务生成。 - Markdown 计划导出/复制。

验收： - 无外部 API 时可完整运行。 - 输出任务有可验证的验收标准。 -
用户自评与验证证据清楚区分。 - 不存在虚构资源 URL
或无依据的精确时间承诺。

## M6：质量收尾与公开发布（第 6--8 周）

交付： - 响应式和可访问性修正。 - 数据核验、社区规范、隐私说明。 -
发布检查清单、已知限制和路线图。 - 首批真实竞赛、技能、项目和资源条目。

验收： - 核心流程端到端通过。 -
构建、类型检查、测试、数据校验全部通过。 -
关键页面无明显移动端布局问题。 -
页面上没有假数据、假用户数或虚构评分。 -
官方来源、核验日期和免责声明可见。 -
维护者能根据贡献指南独立处理一次新增竞赛 PR。

-   采用简洁、现代、信息密度适中的技术社区风格。
-   优先响应式布局，手机与桌面均可使用。
-   使用统一的设计 token、排版、间距、颜色和组件。
-   支持键盘导航、可见焦点、语义化 HTML 和足够对比度。

-   为加载、无结果、无数据、出错和待核验状态提供明确 UI。
-   不要只做一个静态截图式首页；必须实现真实路由、真实数据读取和可工作的交互。
-   不使用假统计、假排行榜和无意义的装饰性图表。

14. 所有公开内容均应能追溯到来源或明确标注为观点/示例。

阶段 3：实现首页、竞赛目录、搜索筛选、详情页与深层路由。

阶段 4：实现评分引擎、正式排名准入规则、排行榜和评分方法页面。

阶段 5：实现项目成果、经验内容、技能图谱和社区入口。

阶段 6：实现成长规划器、技能依赖拓扑排序、任务验收标准和 Markdown 导出。

阶段 7：完善 GitHub Discussions 指引、Issue/PR

阶段 8：完成移动端、可访问性、SEO、测试、数据审核和 GitHub Pages

-   没有虚构的官方数据、用户数据、统计数据和链接。

-   README 包含本地运行、构建、测试、数据贡献和部署步骤。
-   所有未完成项目、限制和后续工作被如实列出。

# 16. 最终产品决策摘要

-   **定位**：大学生科技竞赛信息与成长规划的开源平台。
-   **首版架构**：React + TypeScript + Vite，GitHub Pages 静态托管。
-   **内容维护**：Markdown + JSON，所有数据通过 PR 管理。
-   **社区**：GitHub Discussions + Issues + Pull Requests。
-   **评分**：公开维度、版本化权重、证据分级、缺失数据规则和准入门槛。
-   **成长建议**：确定性规则引擎优先，技能依赖图与可验证任务为核心。
-   **成本**：首版尽量使用 GitHub 公共仓库和免费额度；Actions
    额度和平台政策以官方最新文档为准。
-   **扩展**：达到真实需求后再引入后端 API、PostgreSQL、账户和动态评分。
-   **第一优先级**：建立可信的数据模型和贡献流程，再扩大数据量与功能范围。

项目能否长期成功，取决于竞赛数据是否可信、贡献是否方便、评分是否可解释，以及学习建议是否真的帮助用户完成项目，而不只是页面是否漂亮。
