## 可复现不是“我电脑上能跑”

一个项目可复现，意味着另一个人在**没有你的口头解释**的情况下，能按文档得到相同或可解释的结果。竞赛提交、项目展示和开源协作都依赖这一点。

下面是一份可以逐项勾选的清单。不要为了全部打勾而编造信息；做不到的项就写“未验证”或“已知限制”。

## 一、环境

- [ ] 写清操作系统与版本（例如 Ubuntu 22.04、Windows 11）。
- [ ] 写清运行时版本（例如 Node.js 22、Python 3.12）。
- [ ] 写清必须的系统依赖（编译器、驱动、SDK）。
- [ ] 如果依赖特定硬件，写清型号、固件版本与接线。
- [ ] 说明哪些步骤需要联网，哪些可以离线完成。

## 二、依赖

- [ ] 使用锁文件或固定版本（`package-lock.json`、`requirements.txt`、`poetry.lock` 等）。
- [ ] 不在文档里写“安装最新版”这种不可复现的指令。
- [ ] 记录第三方模型、数据集或二进制的来源与许可。
- [ ] 如果依赖私有资源，明确说明获取方式；没有授权就不要提交。

## 三、数据

- [ ] 说明数据来源、访问日期与许可。
- [ ] 提供小规模示例数据，避免仓库过大。
- [ ] 写清字段含义、缺失值与异常值处理。
- [ ] 不提交包含个人信息、密钥或未授权内容的数据。
- [ ] 如果数据不能公开，提供可生成合成数据的脚本，并明确它不是原始数据。

## 四、运行步骤

- [ ] 从干净环境开始，按 README 逐步执行。
- [ ] 每条命令可直接复制，包含必要参数。
- [ ] 写清预期输出或成功标志。
- [ ] 记录常见错误与排查方向。
- [ ] 至少请一位没有参与开发的人独立试跑，并记录卡点。

一个合格的 README 至少包含：

```text
# 项目名
一句话说明 + 当前状态

## 环境
## 安装
## 运行
## 测试
## 数据与许可
## 已知限制
```

## 五、测试与结果

- [ ] 提供可一键运行的测试命令。
- [ ] 测试覆盖关键路径与至少一个失败路径。
- [ ] 报告指标时写清数据集、划分、随机种子与依赖版本。
- [ ] 不只展示最好结果；给出基线、失败案例与限制。
- [ ] 图表有标题、单位、样本范围与文字说明。

## 六、许可证与第三方材料

- [ ] 代码有明确许可证。
- [ ] 文档与图片的授权状态写清楚。
- [ ] 第三方代码、模型、字体、图标保留原许可证与署名。
- [ ] 不把“可免费阅读”写成“允许转载”。
- [ ] 团队成员的名字、角色与贡献已获得发布同意。

## 七、提交前的 10 分钟检查

1. 在一个新目录重新 clone。
2. 按 README 安装依赖。
3. 运行测试。
4. 运行一次最小示例。
5. 打开所有外链，确认没有 404 或占位地址。
6. 搜索仓库，确认没有密钥、令牌、手机号或真实姓名。
7. 检查大文件与构建产物是否误提交。
8. 让一位队友按文档复述运行步骤。

## 八、已知限制怎么写

限制不是减分项，隐瞒才是。可以这样写：

```text
## 已知限制
- 仅在室内光照下测试，强逆光场景未验证。
- 数据集只覆盖 3 个类别，跨类别泛化未知。
- 实时性在 1080p 下低于 10 FPS，未做模型量化。
```

每一条限制最好对应一个“下一步验证方法”，让读者知道边界在哪里。
