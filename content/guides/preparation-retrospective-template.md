## 为什么需要复盘模板

比赛结束后，记忆会迅速衰减。没有记录的复盘容易变成两种东西：获奖感言，或者情绪总结。模板的作用不是让你写得漂亮，而是强迫你留下**可验证的事实**与**可复用的判断**。

下面的结构可以直接复制到 Markdown 文件。删掉不适用的部分，但不要删掉“证据”和“失败”两节。

## 一、基本信息

```text
竞赛名称：
参赛年份/届次：
赛道/组别：
团队规模与角色：
最终结果（如不便公开可写“未公开”）：
官方来源：
```

结果不是复盘的核心。没有获奖也可以写；关键是区分“结果”与“过程”。

## 二、目标与假设

开赛前你想验证什么？写 2–3 条可检验的假设，例如：

- 我们能在 6 周内完成一个可运行的巡线原型；
- 视觉方案在室内光照下可达到 10 FPS；
- 三人分工可以覆盖机械、电控与文档。

然后逐条写：**成立 / 部分成立 / 不成立**，以及判断依据。没有依据的“感觉”不算结论。

## 三、时间线与关键决策

只记录改变方向的节点，不必写流水账：

| 时间    | 决策/事件              | 备选方案   | 为什么这样选   | 事后看是否合理   |
| ------- | ---------------------- | ---------- | -------------- | ---------------- |
| 第 2 周 | 放弃视觉方案，改用红外 | 继续调参   | 现场光照不可控 | 合理，但发现太晚 |
| 第 5 周 | 缩减功能，保底完成     | 全功能冲刺 | 联调时间不足   | 合理             |

“事后看是否合理”要写理由，不要只写“后悔/不后悔”。

## 四、证据清单

把“我们做了什么”变成可检查的文件：

- [ ] 代码仓库与提交记录（含 README）
- [ ] 关键实验的原始数据与脚本
- [ ] 测试记录（输入、预期、实际）
- [ ] 硬件版本、接线图与物料清单
- [ ] 演示视频或现场照片（注意隐私与授权）
- [ ] 提交材料与答辩 PPT
- [ ] 官方规则/通知的存档链接与访问日期

证据不需要多，但要能支撑你的结论。没有证据的结论，在复盘里标成“推测”。

## 五、失败与限制

至少写三条，按“现象 → 假设 → 验证 → 结论”组织：

1. **现象**：联调时电机间歇失控。
2. **假设**：电源压降导致复位。
3. **验证**：示波器记录到 3.3V 轨在启动瞬间跌到 2.7V。
4. **结论**：电源余量不足；下次在方案阶段做峰值电流预算。

失败不是“能力不行”的证据，而是下一次设计的输入。把失败写成可复用的检查项，比写“以后注意”有用。

## 六、能力变化

对照技能图谱，给自己写“参赛前 / 参赛后”的自评，并标注证据：

| 技能     | 赛前自评 | 赛后自评 | 证据                                   |
| -------- | -------- | -------- | -------------------------------------- |
| 嵌入式 C | L1       | L2       | 完成定时器采样与串口模块，有测试       |
| 技术写作 | L1       | L2       | 提交 README 与答辩稿，队友可按文档复现 |

自评仍然是自评。证据列是给未来的自己和评审看的，不是自动认证。

## 七、如果重来一次

写 3 条“下一次会提前做什么”，要求具体到动作：

- 在第 1 周就确定集成负责人和每日联调窗口；
- 在第 3 周做一次“只保底功能”的演示；
- 所有关键器件准备备件，并记录替换步骤。

不要写“更努力”“多沟通”这类无法验收的建议。

## 八、可复用的产出

最后列出可以沉淀为社区内容的材料：

- 一篇技术拆解；
- 一份可复现的 checklist；
- 一个最小示例仓库；
- 一次失败教训的公开记录。

发布前确认：不包含他人未授权的代码、论文、图片或个人信息；涉及队友的内容已获得同意。
